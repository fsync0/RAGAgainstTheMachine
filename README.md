# RAG Against the Machine

## Description

This project is a local Retrieval-Augmented Generation (RAG) system for
answering questions about the provided vLLM codebase. Its goal is to find the
most relevant source-code or documentation snippets for a question, then use
those snippets as context for an answer generated by `Qwen/Qwen3-0.6B`.

The system loads Python, Markdown, and text files, splits them into small
chunks, indexes the chunks with BM25, retrieves the best matching chunks, and
generates an answer grounded in their text. It also supports batch retrieval
and Recall@k evaluation with JSON datasets.

## System architecture

```text
                         Indexing pipeline

data/raw/ → Loader → SourceFile → Chunker → SourceChunk → BM25 → bm25.pkl

                          Query pipeline

Question → Retriever → best SourceChunks → prompt → Qwen/Qwen3-0.6B → answer
```

The `Indexer` coordinates loading, chunking, and index storage. The
`Retriever` loads the saved index and returns the highest-ranked chunks. The
`Generator` receives a question and the retrieved chunks, creates a grounded
prompt, and generates the final answer.

## Chunking strategy

The project uses `RecursiveCharacterTextSplitter` from
`langchain-text-splitters`.

- Python files use Python-specific separators, so the splitter prefers useful
  code boundaries such as classes and functions.
- Markdown and text files use Markdown separators to preserve headings and
  paragraphs when possible.
- Chunks have no overlap and are capped at 2000 characters, which is the
  maximum source length accepted by the evaluator.
- Every `SourceChunk` keeps its original `file_path`,
  `first_character_index`, and `last_character_index`. This makes retrieved
  locations traceable to the original corpus.

## Retrieval method

The retrieval method is BM25, implemented with `rank-bm25`.

At indexing time, the system tokenizes both the chunk text and its file path.
Including file-path tokens helps retrieve code when a question contains a
module, function, or identifier name. At query time, BM25 calculates a score
for every chunk and returns the top `k` scores.

BM25 is a lexical method: it matches words instead of meaning. It gives more
importance to rare words, limits the benefit of repeating the same word, and
adjusts scores for chunk length. These rules make it suitable for ranking code
and documentation chunks.

## Design decisions

- **BM25 instead of embeddings:** BM25 is a required lexical method, is fast
  on CPU, and works well for identifiers and exact technical terms.
- **File paths are indexed:** code questions often include names that appear in
  paths, not only in source text.
- **Pydantic records between stages:** validated models make source locations,
  datasets, search results, and answers predictable.
- **Separate Python and Markdown/text splitting:** code and documentation have
  different useful boundaries.
- **Lazy Qwen loading:** the model only loads for answer commands. Dataset
  answering reuses one generator, so model weights load once.
- **Configurable paths:** CLI paths are arguments rather than hard-coded so the
  evaluator can choose its own input and output locations.

## Performance analysis

The public datasets were evaluated with the provided Moulinette at `k = 5`.

| Dataset | Recall@5 | Required |
|---|---:|---:|
| Documentation | 81.0% | 80.0% |
| Code | 59.6% | 50.0% |

Both results meet the mandatory retrieval threshold. Indexing creates about
14,500 chunks and completes in a few seconds on the tested machine. Batch
retrieval also completes within the required limit. Retrieval quality depends
on chunk size, tokenization, and whether query words appear in the source text
or file path.

## Challenges faced

- **Exact source paths and locations:** the evaluator compares source paths
  exactly. The loader keeps project-relative paths and the chunker keeps the
  original character positions.
- **Chunk size limit:** retrieved sources must not exceed 2000 characters. The
  CLI caps the requested size and the chunker enforces the same limit.
- **Code retrieval:** natural-language questions may not use the exact words
  in code. Indexing file-path tokens improved retrieval of modules and
  identifiers.
- **Local model cost:** Qwen can be slow to load on CPU. The generator loads
  lazily and one instance is reused for all questions in `answer_dataset`.

## Instructions

### Requirements

- Python 3.10 or newer
- [uv](https://docs.astral.sh/uv/)
- The vLLM source corpus under `data/raw/`
- Question datasets under `data/datasets/`

The corpus, datasets, generated indexes, outputs, and model weights are not
committed to the repository.

### Installation

```bash
uv sync
```

### Project layout

```text
src/                                    Application source code
data/raw/                               Source corpus to index
data/processed/                         Saved BM25 index
data/datasets/                          Question datasets
data/output/search_results/             Dataset search JSON output
data/output/search_results_and_answer/  Dataset answer JSON output
```

### Example usage

Build the index once:

```bash
uv run python -m src index --max_chunk_size 2000
```

Search one question:

```bash
uv run python -m src search "How to configure the OpenAI server?" --k 5
```

Search a dataset:

```bash
uv run python -m src search_dataset \
  --dataset_path data/datasets/UnansweredQuestions/dataset_docs_public.json \
  --k 5 \
  --save_directory data/output/search_results/UnansweredQuestions \
  --index_path data/processed
```

Answer one question:

```bash
uv run python -m src answer "What is the default timeout?" --k 5
```

Generate answers for a search-results JSON file:

```bash
uv run python -m src answer_dataset \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --save_directory data/output/search_results_and_answer/UnansweredQuestions \
  --index_path data/processed \
  --max_new_tokens 256
```

Evaluate retrieval locally:

```bash
uv run python -m src evaluate \
  --student_search_results_path data/output/search_results/UnansweredQuestions/dataset_docs_public.json \
  --dataset_path data/datasets/AnsweredQuestions/dataset_docs_public.json
```

The official evaluation uses the provided Moulinette executable. This project
does not import or call Moulinette.

### CLI reference

All commands use this format:

```bash
uv run python -m src <command> [options]
```

| Command | Purpose |
|---|---|
| `index --max_chunk_size <int>` | Index source files under `data/raw/`. |
| `search <query> --k <int>` | Print top source locations for one question. |
| `search_dataset --dataset_path <path> --k <int> --save_directory <dir>` | Search a JSON dataset and save `StudentSearchResults`. |
| `answer <query> --k <int>` | Answer one question from retrieved chunks. |
| `answer_dataset --student_search_results_path <path> --save_directory <dir>` | Save `StudentSearchResultsAndAnswer`. |
| `evaluate --student_search_results_path <path> --dataset_path <path>` | Report local Recall@k scores. |

`index` accepts `--raw_path` and `--output_path`. Search and answer commands
also accept an index path. All input and output paths are configurable.

`max_chunk_size`, `k`, and `max_new_tokens` must be positive integers. Chunk
size is capped at 2000 characters.

### JSON output

Dataset search writes this structure:

```json
{
  "search_results": [
    {
      "question_id": "...",
      "question": "...",
      "retrieved_sources": [
        {
          "file_path": "data/raw/vllm-0.10.1/...",
          "first_character_index": 0,
          "last_character_index": 200
        }
      ]
    }
  ],
  "k": 5
}
```

Dataset answer output uses the same structure and adds an `answer` field to
each search result. Output is validated with Pydantic models.

### Makefile

```bash
make install
make run ARGS='index --max_chunk_size 2000'
make debug ARGS='search "What is the default timeout?" --k 5'
make test
make lint
make lint-strict
make clean
```

- `install`: install dependencies with `uv sync`.
- `run`: run the CLI.
- `debug`: run the CLI with Python's debugger.
- `test`: run unit tests.
- `lint`: run flake8 and mypy on `src/` with the required assignment flags.
- `lint-strict`: run flake8 and strict mypy checks on `src/`.
- `clean`: remove Python and type-checker caches.
